# AZ's WP Passkeys specification

AZ's WP Passkeys lets WordPress users sign in with passkeys. Users add, rename, remove and test passkeys from their profile or website pages. Testing a passkey does not change the signed-in account.

The plugin integrates with WordPress login, account policies, administrator permissions and multisite. Its interfaces include native login and profile controls, frontend shortcodes, Gutenberg blocks, site and network settings, and diagnostic tools.

## 1. Product identity and capabilities

The plugin name is **AZ's WP Passkeys**. Its slug and translation text domain are `azwp-passkeys`; its shortcode prefix is `azwp_pk`.

| Area                     | Capability                                                                                                                                                         |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Login                    | Usernameless passkey sign-in: one button opens the browser's passkey picker |
| Login policy             | On/off Passkey only mode; configurable remember-login availability |
| Account policy           | Password login disabling for individual accounts                                                                                                                   |
| Enrollment               | One-click enrollment with automatic `passkey_N` names; every passkey is created as a discoverable credential |
| After registration       | Optional single-site sign-in after WordPress account registration, continuing to passkey enrollment                                                               |
| Management               | Credential list with authenticator model and Synced badge, rename, confirmed removal and policy-availability indicators                                            |
| Testing                  | Verification of a selected account's passkeys without session changes |
| Recovery                 | Administrator-sent one-time passkey setup link for another account |
| Administration           | Authorized management, enrollment and testing for another account                                                                                                  |
| Forgotten-password reset | Unrestricted, restricted except authorized administrators, or restricted for everyone; admin profile password changes remain available under WordPress permissions |
| WordPress interfaces     | Login, own profile, user-edit page, site/network settings and plugin-list links                                                                                    |
| Frontend                 | Login, registration, test and list shortcodes and equivalent Gutenberg blocks                                                                                      |
| Multisite                | Network policies, site settings, shared credential storage and compatible cross-site authentication                                                                |
| Diagnostics              | Configuration warnings and optional logs with manual clearing                                                                                                      |
| Extensions               | Settings rendering/save notification, logger initialization and version query                                                               |
| Lifecycle                | Activation, new-site initialization, deactivation, account/site cleanup and uninstall                                                                              |

Credential registration applies to existing accounts; it does not create WordPress accounts. WordPress creates accounts; the optional after-registration setting in section 4 only signs in a newly created account and opens passkey enrollment. The plugin does not delete credentials from devices or password managers, provide enterprise attestation, operate a cloud service or send account-registration emails.

## 2. Settings and defaults

Settings have typed values and explicit site or network scope. On single-site installations, network-scoped policies apply to that installation.

| Setting                              | Default                                     | Multisite scope |
| ------------------------------------ | ------------------------------------------- | --------------- |
| Website name                      | WordPress site name                         | Site            |
| Passkey domain                                | Host of the site URL                        | Site            |
| Passkey only mode                    | Off                                         | Network         |
| Remember me                       | Disabled                                    | Site            |
| Block password resets                | No                                          | Site            |
| After registration                   | WordPress default                           | Single-site only; not offered on multisite |
| Logging                              | Disabled                                    | Site            |
| Related origins                      | Empty; settings control hidden              | Network         |

The two network settings are Passkey only mode and Related origins. Other settings apply to individual sites.

Account-level password disabling defaults to off and is global user metadata in multisite. Each account has one opaque user handle shared across sites; credentials retain the RP information needed for verification. Every enrollment, login and test requests `userVerification: "required"`. Completion requires the verified UV flag. Fingerprint, face, or device PIN verification is required; devices unable to provide it cannot complete the operation. There is no user-verification setting or override.

User-facing text uses Passkey or passkeys and everyday device wording; it does not use "authenticator" in labels, headings, help or errors, with one exception: the credential list's "Authenticator" column header, which names the model that holds each passkey. Technical contracts use WebAuthn only when naming the protocol, API or library.

### Effective policy on native login

| Condition                                                | Effective behavior                                                                                                 |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Passkey only mode off                                    | Password form with a "Sign in with a passkey" button below it |
| Passkey only mode on                                     | Only the passkey button; password authentication denied for every account; account password-disable checkbox is checked and locked |
| Account password disabled; global mode permits passwords | Password authentication denied for that account; other accounts retain the global preference                       |
| Remember me disabled                                  | Passkey sign-in is never remembered; newly created passkey sessions use WordPress non-remembered duration |
| Remember me enabled                                   | With a password form on the page, passkey sign-in follows that form's Remember Me box. In Passkey only mode the passkey form shows its own Remember me box, initially unchecked |

Network settings override site values for the network-scoped policies; a site cannot weaken them. Password disabling is the logical OR of global Passkey only mode and the account flag. Turning global Passkey only mode off reveals the account's independently stored flag. Activating the plugin leaves Passkey only mode off.

Passkey only mode is strict for browser sessions. While password login is disabled for an account, by global Passkey only mode or by its account flag, a WordPress cookie session for that account is accepted only if a passkey sign-in opened it, or if the after-registration sign-in in section 4 opened it so the account can add its first passkey. The plugin marks those sessions when it creates them. Any other cookie session for the account ends on its next request: its token is destroyed and the request continues signed out. This includes sessions opened with a password before the mode applied, and sessions opened by other plugins. Turning the mode on therefore signs those sessions out, including the administrator's own session if a password opened it. Application Passwords are not cookie sessions and are not affected.

Site settings saves require all declared fields and valid choice values; otherwise the form shows "Settings could not be saved." and retains existing values. Website name and Passkey domain may be saved empty, but enrollment then fails because the site is not configured. Network saves substitute defaults for missing or invalid choice values: prefer passkey. Site saves preserve omitted related origins; network saves replace omitted related origins with an empty list.

## 3. Login and session behavior

With Passkey only mode off, native login shows the WordPress password form with a "Sign in with a passkey" button below it, after an "or". With Passkey only mode on, it shows only the passkey button and hides the username, password, Remember Me and Log In fields, also when JavaScript is off. There is no switch between the two. Passkey login has no identification field: a single "Sign in with a passkey" button requests a discoverable credential, and the browser's passkey picker selects the account. The account is resolved from the verified credential and its user handle.

A login attempt has no client-selected account; completion resolves the account only from the verified credential. A login consists of a challenge, a WebAuthn response and server verification. A new WordPress session is created only if no session exists at completion. Remember-login selection is effective only when enabled by the administrator. WordPress account and cookie restrictions apply as described in section 8. Post-login redirects follow WordPress's normal login behavior as described in section 10.

The interface presents loading, browser passkey prompt, verification, success, retry and fallback states. Cancellation does not lock the account. An unsupported browser sees an explanation in place of the passkey button; the password form stays usable when Passkey only mode is off. Errors do not explicitly disclose whether an unknown account exists.

There is no conditional UI (passkey autofill) on native or frontend login; passkey sign-in always starts from the explicit button.

A successful login assertion reports "Passkey verified." and attempts to update the verified credential's last-used time under section 13. When a WordPress session already exists at completion, login does not replace or refresh that session, even if the verified credential belongs to another account. Credential tests never switch the session identity.

## 4. Enrollment and credential management

Enrollment requires an authenticated account, valid CSRF protection and authorization for the target account. Enrollment options contain the target account identity, RP and the default credential name, fixed when the options are issued; completion sends no name. Each enrollment attempt is bound to its initiating actor, login session and target account. Completion must match all three and recheck the actor's permissions for that target. Changed or expired context requires a fresh enrollment attempt; it does not trigger a recent-authentication requirement.

Registration supplies all credentials associated with the account as exclusions, including credentials enrolled on other sites. Attestation preference is direct, so the browser returns the authenticator's real AAGUID; the user's browser may ask before sharing a security key's make and model, and a declined prompt yields none attestation. All supported passkeys can be enrolled; user verification is required. Creation options always require a resident (discoverable) credential. Registration reports success only after persistence of the intended credential for the intended account is confirmed. Success displays "Passkey added." and refreshes the credential list. Handled registration failure or browser passkey prompt cancellation also refreshes the list. Confirmed persistence failure reports registration failure and makes a fresh registration attempt available. Registration leaves any existing WordPress session unchanged. The device or password manager may retain a passkey created during a failed registration; the plugin cannot remove that passkey automatically. A lost response or otherwise uncertain persistence outcome is reported as uncertain rather than as proof that no credential was saved. Refreshing the credential list can establish whether the intended credential is present.

Adding or deleting passkeys does not require recent authentication or a five-minute reauthentication gate. Session, capability, nonce/CSRF and transaction-ownership checks apply to both self-service and administrator operations.

Credential lists show names, the authenticator model, registration and last-use times and policy restrictions. The model comes from the bundled authenticator catalog keyed by the credential's stored AAGUID, described in section 26; an unknown or all-zero AAGUID shows "—". A credential whose stored backed-up flag is set shows a "Synced" badge under its model; the flag is self-reported by the authenticator and refreshed by each accepted sign-in or test. Unavailable actions have explanatory states. Names are display labels, escaped as text rather than executable content.

Rename requires authorization and CSRF protection. Removal requires confirmation and the usable-access rule in section 6. Removal deletes the server-side registration; the credential can remain on the user's device or password manager. Rename and removal report success only when the intended stored state is confirmed. A confirmed write failure produces an operation error and displays the actual stored state when available. An uncertain outcome offers a list refresh without claiming success or failure. An unchanged name is a confirmed no-op only when the target exists with that name. An already-absent credential is reported as absent once confirmed, rather than as a database error or a newly performed deletion. These outcomes retain the same account/site authorization and usable-access safeguard.

Every confirmed enrollment emails the account owner at their WordPress email address, in the owner's locale. The email names the passkey and the site, says whether the owner or another named account added it, and links to the owner's profile with advice to remove an unexpected passkey and change the password. It is sent after the credential is saved; a mail failure does not change the registration result. There is no setting to turn it off.

### Enrollment controls and outcomes

Enrollment asks for no name. Clicking "Add passkey" starts the browser ceremony directly. Each new passkey receives the default label `passkey_N`, where N is the lowest positive number that none of the account's passkeys uses; the owner can rename it afterwards. Duplicate labels are allowed; labels do not identify credentials. The rename prompt rejects an exactly empty input.

Every passkey is enrolled as a discoverable credential with required UV; there is no enrollment choice. Authenticators that cannot store discoverable credentials report the normal registration failure.

Profile management shows an "Add passkey" button that starts registration immediately and a "Test passkey" button that starts the test immediately; both report progress and results in one status line beneath them. After the native registration continuation, the Add passkey button receives focus. Enrollment controls are separate from the WordPress profile-save form; enrolling a credential does not submit unrelated profile changes. Pending frontend operations disable the page's passkey action buttons and the first embedded traditional form submit button together. Cancelling the browser passkey prompt displays a failure state and restores controls. Duplicate credential enrollment fails without replacing ownership.

### Passkey setup link

An administrator with `edit_user` for another account can click "Send passkey setup link" on that account's profile. The plugin emails the account owner, in the owner's locale, a one-time link to `wp-login.php?action=azwp_passkeys_setup` carrying the account ID and a random 32-byte token. The administrator never sees the link, so it cannot add the administrator's own device to the account. An account cannot send a link to itself.

The account stores at most one pending link in the `azwp_passkeys_setup_link` user meta. It holds the SHA-256 hash of the token, its expiry, the issuing administrator and the issuing site. A link expires after one hour and works only on the site that issued it. Sending another link replaces it. Opening the link only checks it, because mail scanners open links before people do. The page shows "Add a passkey for <username>." and an Add passkey button, or "This passkey setup link has expired or was already used. Ask a site administrator for a new one."

The button runs a registration ceremony with purpose `setup`, bound to the browser like a sign-in attempt and rate limited like anonymous sign-in. A signed-in visitor must be the link's own account. Completion uses up the link inside the owner lock, in the same transaction that saves the passkey, so a link is used up only when a passkey is saved. The browser then goes to the sign-in page, which says "Passkey added. Sign in with it now." The link never signs anyone in. The owner receives the section 4 enrollment email, which names the administrator who sent the setup link. If the email cannot be sent, the request fails with `mail_failed` and "The email could not be sent. Try again." A new link replaces the pending one only after its email is sent, so a failed send leaves the owner's earlier link working.

### Sign-in after account registration

"After registration" has two choices: "WordPress default" and "Sign in and add a passkey". WordPress default is the default and leaves WordPress account registration, its welcome email and its "check your email" continuation unchanged. The setting exists only on single-site installations, where WordPress's native `wp-login.php?action=register` form creates accounts; multisite signup and activation (`wp-signup.php`, `wp-activate.php`) are unchanged and the control is not rendered there. The setting has no effect while WordPress's "Anyone can register" option is off.

With "Sign in and add a passkey", a newly registered account that WordPress created through the native registration form is signed in by that registration request and sent to its own profile with the Add passkey button focused. The account is created, and its welcome email sent, by WordPress exactly as under the default; the plugin does not create the account, does not collect a password and does not create a passkey during registration. Enrollment then follows the normal rules in this section: an authenticated account, the management nonce, and the actor/session/target binding. A passkey is never added to an account that is not yet signed in.

Sign-in after registration happens only when all of these hold; otherwise the request falls through to WordPress's normal registration continuation without a session or an error:

- The request is the native single-site registration request that just created the account.
- The registration form was submitted from the site itself: the request's `Origin` header, or the origin of its `Referer` header when `Origin` is absent, exactly matches one of the site's permitted origins in section 23. A missing, `null` or foreign origin fails this check. WordPress's registration form has no nonce, and a nonce issued to logged-out visitors is the same for every visitor, so the origin check is what prevents a cross-site form from signing a victim's browser into an account the attacker controls.
- No WordPress session already exists in the request. An existing session is never replaced, matching section 3.
- The new account passes the account-eligibility checks in section 24, including a `WP_Error` from other plugins (for example manual approval).
- WordPress permits auth cookies for the request; a suppressed cookie leaves the account signed out.

Account creation is never affected by these checks. A failed check only means the new account is not signed in by the plugin.

The new session is non-remembered regardless of the Remember me setting. Global Passkey only mode and the account password-disable flag do not block this sign-in, because no password is used; they continue to apply to every later password sign-in. The password-reset modes in section 6 are unchanged. This sign-in is not a passkey sign-in, so the Two-Factor exception in section 8 does not apply to it. When Two-Factor requires a challenge for the new account, its own flow takes over the request at `wp_login` and the profile redirect does not occur. The session Two-Factor opens after its challenge carries no plugin mark, so under Passkey only mode it ends on its next request.

This setting signs in an account whose email address WordPress has not yet verified. Its help text states that risk. The usable-access rule in section 6 still governs removal. A new account that leaves without adding a passkey keeps only the sign-in methods its policies allow. WordPress's welcome email sets a password through a native reset link (`wp-login.php?action=rp`), so it works only when "Block password resets" is No. In the restricted reset modes that link returns to login. In Passkey only mode the welcome email has no set-password link at all, as section 6 describes. A new account that cannot sign in gets back in through a passkey setup link that an administrator sends, or through an administrator changing its policy. A passkey that an administrator adds directly would live on the administrator's own device. The self-account notice in section 6 links to enrollment while the session lasts.

On arrival, the profile shows "Your account is ready. Add a passkey so you can sign in next time." above the Add passkey button. The arrival marker is a UI hint only: it grants no authority and is ignored on other users' edit pages. The server cannot tell a new account from an existing one by the marker, so any own-profile page opened with it shows the same message and focused Add passkey button.

Lists are ordered by registration time, oldest first. A never-used credential displays a dash for last use. Empty lists display "No passkeys added." A credential that is unusable under the current site settings shows an explanation and remains renameable and removable subject to the removal rule.

## 5. Credential tests

Profile and frontend interfaces provide one credential test, "Test passkey". It verifies the selected account's passkeys through an explicit allow-list. Tests use the same verification and effective-policy rules as authentication, with a distinct test purpose bound to the ceremony.

Successful tests follow the security-state and last-used persistence rules in section 13, create no authentication cookie and do not change the logged-in account. An authorized administrator can test the selected account's passkeys.

## 6. Password policy, reset and usable access

Turning on password-login disabling for an account requires that account to hold at least one passkey that is usable under the current site settings; the check and the write run under the owner lock, so a concurrent request cannot remove the last passkey between the check and the write. An account that is already password-disabled can still save unrelated profile changes. Turning on site Passkey only mode, or network Passkey only mode on multisite, requires the administrator who saves it to hold a usable passkey. Saving the setting again while it is already on skips this check. When the check fails, the save fails and the field says "Add a working passkey to your own account before turning on Passkey only mode." The account-level refusal says "Add a working passkey before turning on Passkey only mode for this account." Other accounts without passkeys do not block the save. Instead the Passkey only mode control shows a readiness warning. It gives the number of site members with no passkey stored for the site's Passkey domain. On single-site every account counts as a member, as on the Users screen; on multisite, members are accounts with a role record on that site. The warning links to the Users screen filtered to them (`users.php?azwp_passkeys_missing=1`). On the network settings page the count covers every site in the network and the links are per site. When an administrator turns the mode on while that count is above zero, the browser asks "N accounts have no working passkey and will not be able to sign in. Turn on Passkey only mode anyway?". Cancelling keeps the mode off. Confirming submits a token in `passkey_only_confirmed` that identifies the exact set of listed accounts; without JavaScript a checkbox submits the same token. The server recomputes the set and refuses the save unless the token matches, so a stale page cannot approve a different set of accounts, even one of the same size. The refused save says "Confirm that the accounts listed above will not be able to sign in, then save again." Turning the mode off, or turning it on when the count is zero, needs no confirmation. These checks use the stored Passkey domain, so a site settings save that leaves Passkey only mode on cannot change the Passkey domain or empty the Website name. Either change would stop every passkey from working. Such a save fails and the field says "Passkey only mode is on, and changing this would stop every passkey from working. Turn Passkey only mode off first." A save that turns the mode off may change them.

Network/site Passkey only mode policy and individual password-login disabling determine whether an account can sign in with its password. They do not prevent storing or changing that password, using it for unrelated legitimate WordPress operations, or using unrelated administration functions. While Passkey only mode is on, a reset would only produce a password that cannot sign in, so password resets behave as "For everyone" whatever this setting says, and the settings page notes it. WordPress cannot build its welcome email without a reset key, so the plugin allows that one key request, made right after `wp_send_new_user_notification_to_user`. The reset pages stay blocked, so the key is useless. The plugin also removes the set-password link from WordPress's welcome email. The email names the account, explains that accounts on this site sign in with passkeys only, asks the user to request a passkey setup link from an administrator and links to the sign-in page. The "Block password resets" setting has three choices:

| Mode                             | Behavior                                                                                                        |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| No                               | Standard WordPress password-reset behavior                                                                      |
| Except for administrators        | Reset permission is available to actors with edit_users; this filter exception does not exempt native forgotten-password/reset URLs, which remain redirected |
| For everyone                     | Forgotten-password reset is restricted in both the interface and server handling                                |

Reset restrictions apply independently of the secure-context warning. Configured global and account-level password-login restrictions remain enforced regardless of HTTP/HTTPS detection. An insecure request or incorrectly detected HTTPS never silently enables prohibited password login. If HTTPS or passkey configuration leaves no usable sign-in method, an operator may need to correct the configuration. The notices below identify accounts with no passkey enrolled on the current site.

Credential removal is blocked when it would leave the account without a usable sign-in or recovery method. The user first needs another usable passkey or another way to sign in. The assessment includes RP compatibility, required verification, account state, and effective account/site/network password and reset restrictions. Raw credential count alone is insufficient. Password reset is not a recovery method when the resulting password still cannot be used to sign in.

The access assessment and deletion are atomic: concurrent removals cannot each rely on the credential being removed by the other request. Global account policies and cross-site credential usability are included in the assessment.

There is no administrator exemption from this removal rule. Password-policy settings warn about loss of access.

### Password and reset controls

| Operation                                               | No                                                                | Except for administrators                                         | For everyone                                           |
| ------------------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------- |
| Public lost-password request and reset-token completion | WordPress behavior                                                | Denied; native reset pages return to login                        | Denied; native reset pages return to login                        |
| Lost-password link                                      | WordPress behavior                                                | Hidden                                                            | Hidden                                                            |
| Own admin profile password fields/change                | Visible and usable under normal WordPress permissions             | Visible and usable under normal WordPress permissions             | Visible and usable under normal WordPress permissions             |
| Other-user admin password fields/change                 | Visible and usable under normal WordPress target-edit permissions | Visible and usable under normal WordPress target-edit permissions | Visible and usable under normal WordPress target-edit permissions |
| Passkey enrollment/login/test                           | Passkey policy                                                    | Passkey policy                                                    | Passkey policy                                                    |

The administrator exception for forgotten-password reset permission is based on the acting user's `edit_users` capability. Admin profile and user-edit password changes follow normal WordPress nonce, capability and target-account protections, independently of that reset exception. Their password fields remain visible and usable in every reset mode and when global or account password login is disabled. The administrator reset-permission exception does not make native reset URLs usable: anonymous visitors and administrators are redirected in both restricted modes. It is not counted as a usable native recovery method; normal authorized admin profile password changes remain separate. Password-reset restrictions do not independently disable password authentication; password-login policy does not independently enable reset. Reset restrictions suppress the new-account default-password reminder.

The profile account-password checkbox is saved through normal authorized profile saving. In global Passkey only mode it cannot weaken the global restriction. On every non-network administration page, a self-account notice warns when password login is disabled and the account has no credential enrolled on the current site; the self-account notice links to enrollment. User-edit pages also show the selected target warning; network administration suppresses these notices. A subdirectory multisite notice also explains that credentials from other network sites may work. These notices use site credential count, separately from the check that a usable sign-in or recovery method remains for deletion.

## 7. Administrator permissions

Site settings require `manage_options`; network settings require `manage_network_options`. Operations on another account require `edit_user` for that target and appropriate profile access. Self-management requires an authenticated account with read capability. Authorization depends on capabilities rather than role names.

An authorized administrator can list, enroll, rename, remove and test credentials for another account, and change its password-login policy. The interface identifies the target account. Actor and target remain distinct throughout authorization, ceremony completion and diagnostics.

Administrator add/delete operations have no recent-authentication requirement. Removal uses confirmation and the same usable-access rule as self-service. Enrollment has no additional confirmation prompt; the account owner receives the section 4 notification email.

Self-service enrollment, listing, rename, removal and tests require an authenticated user with `read`. Other-user endpoint operations require that baseline plus `edit_user` for the target. The other-user profile interface and its save handler are registered only for actors with `edit_users`; saving the account-password flag also checks the target-specific profile nonce and `edit_user`. Settings require their site/network settings capability; log read/clear uses manage_options. Capability checks apply on every request, including completion; interface visibility alone grants no authority.

## 8. WordPress authentication integration

Cryptographic verification establishes credential proof; account and session policies determine whether that proof can produce a WordPress login. The session integration honors account existence/status, applicable restrictions, remember-login policy, cookie policy and appropriate login events.

Successful passkey login skips the named Two-Factor plugin's additional challenge. This exception is limited to that integration and the successful passkey request. Unrelated authentication hooks, disabled-account checks and cookie restrictions remain effective. Required user verification applies independently.

A placeholder password or client-supplied user identity is not authentication proof. A downstream rejection remains a failed login; it cannot be replaced with success. Session creation follows successful verification and account-policy approval.

The explicit authentication-plugin integration is Two-Factor.

## 9. Diagnostics page

The Tools menu in site administration contains Passkey diagnostics, with page slug `azwp-passkeys-diagnostics` and title "Passkey diagnostics". Access requires `manage_options` for the current site. The page contains the logging control, its Save changes button, existing environment/configuration warnings, entry count, log viewer and Clear logs action. Logs remain site-scoped in multisite; there is no network-wide log viewer.

The site settings page links to Passkey diagnostics, and the diagnostics page links back to site settings. Logging controls and log entries appear only on the diagnostics page. Contextual warnings next to affected login, enrollment and policy controls remain in place. Diagnostic behavior, redaction and retention follow section 15.

## 10. Frontend shortcodes and blocks

| Shortcode            | Attributes and defaults                                      |
| -------------------- | ------------------------------------------------------------ |
| `[azwp_pk_login]`    | `traditional=true`; `username=''`; `auto_hide=true`; `to=''` |
| `[azwp_pk_register]` | `display=true`                                               |
| `[azwp_pk_test]`     | `display=true`                                               |
| `[azwp_pk_list]`     | `display=true`                                               |

For the display attribute, true shows a logged-out message and false hides the component from logged-out visitors. Login supports the password form beside the passkey button, a prefilled username or email address, logged-in hiding, remember-login policy and destination selection. Registration enrolls credentials for an existing authenticated account.

Four Gutenberg blocks expose login, registration, test and list capabilities. Their saved content is the corresponding shortcode with the configured attributes. Block identifiers and serialization are defined in section 25.

Multiple components can be inserted. Their frontend controls share page-level behavior: toggling targets the first login form, login pending state disables the page's passkey actions, and redirect selection uses the first matching destination field.

### Attribute and editor behavior

| Control     | Type/default  | Meaning                                                                                                                                            |
| ----------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| traditional | Boolean, true | Includes the password form when Passkey only mode is off; false omits it |
| username    | Text, empty   | Prefills the embedded password form's username or email field; passkey sign-in has no identification field |
| auto_hide   | Boolean, true | Hides login from authenticated users with read capability                                                                                          |
| to          | URL, empty    | Requested destination passed through WordPress's normal login redirect handling; empty uses the containing page as the frontend return destination |
| display     | Boolean, true | For logged-out visitors, true shows a message and false renders nothing; authorized logged-in visitors receive the component in either case        |

Shortcode booleans use string comparison: only the literal `true` enables traditional, auto_hide or display; other supplied values act as false. Omitted attributes use the table defaults. Blocks expose the same defaults using checkbox controls for booleans and text controls for username/destination. The login block has all four login controls; each other block has only display. Editor controls cannot override authentication policy.

With `traditional` true and Passkey only mode off, frontend login shows the password form followed by the passkey button. When `traditional` is false or Passkey only mode is on, only the passkey form appears. An unsupported browser sees an explanation in place of the passkey button. The account-password restriction is enforced after identification even when a generic password form is visible.

With auto_hide false, an authenticated visitor can see and submit the login component. A successful assertion for either the current account or another account displays "Passkey verified.", attempts the last-used update under section 13 and follows the redirect/reload path. The current session and its cookie remain unchanged. There is no sign-out prerequisite.

Post-login navigation follows WordPress's normal login redirect behavior, including the login_redirect filter, capability-sensitive and multisite destinations, and WordPress redirect safety functions and filters. Native and frontend passkey login supply the requested redirect_to value; without a requested destination, WordPress supplies its administration destination and applicable account-specific routing. Users without edit_posts normally reach their profile when they have read capability, or the home page otherwise. Multisite applies WordPress's user-admin and dashboard routing. The traditional password form retains the core login-page continuation. Passkey AJAX completion returns a safe destination and inline outcomes; it does not reproduce administrator email confirmation or the interim-login response document, as detailed in section 24.

Frontend login supplies the form's requested destination to the same WordPress login redirect handling. An explicit shortcode to value is a requested destination, not an unconditional navigation command. With no explicit destination, the frontend return destination is the containing page, following wp_login_form's default. Existing page-level destination-field selection supplies only an input to this server-side handling. The embedded password form retains WordPress's normal submission behavior. Login filters may change the destination.

WordPress controls redirect validation and fallback through wp_safe_redirect, wp_validate_redirect, allowed_redirect_hosts and wp_safe_redirect_fallback where applicable in the normal login flow. The default allowed host is the home_url host; WordPress validates relative destinations and HTTP/HTTPS URLs. Unsafe destinations use the core fallback, which defaults to admin_url and is filterable. The plugin adds no separate host allowlist, redirect setting or fallback policy. Browser navigation uses the server-resolved result rather than bypassing WordPress handling with a raw field or URL parameter. Errors and cancellation do not redirect. The `username` shortcode attribute prefills only the embedded password form and is sanitized as plain text. The password form retains WordPress identification handling.

## 11. Multisite behavior

Network activation initializes shared credential storage and the applicable settings. Individual sites, including newly created sites, receive their required site state. Records identify the account owner, enrollment site and RP.

Management lists, rename and removal are scoped to the enrollment site. Authentication can use credentials enrolled elsewhere for the same account when RP and origin compatibility permits it. Shared storage alone does not enable cross-domain authentication. Account password disabling remains global.

Removing site membership deletes credentials enrolled on that site. Network-user deletion removes all of the user's credentials. There is no separate site-deletion credential sweep; membership-removal events perform their own site-scoped cleanup. Super-admin and membership access follow explicit capability and target-account checks.

Subdirectory, subdomain and mapped-domain installations depend on RP/origin verification.

### Access and cleanup scope

Multisite activation is network-wide. Site settings remain individually configurable; network policy applies on every site. A user's ability to manage credentials on a site follows that site's `read` capability and WordPress target-edit authorization. Super-admin status is evaluated through WordPress capabilities, not a hard-coded role-name exemption.

Authentication uses the receiving site's RP/origin and site settings together with network policies and the global account flag. A compatible credential does not itself grant site membership or bypass WordPress account/access rules. Different RP IDs require separate enrollment; mapped domains do not gain compatibility from sharing a network.

| Lifecycle event                                             | Credential and state outcome                                                                                                                    |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Voluntary credential removal, including by an administrator | Usable-access rule enforced atomically                                                                                                          |
| Site membership removal                                     | Credentials enrolled on that site removed; other-site credentials and global account flag retained                                              |
| Site deletion                                               | WordPress removes site-local data; plugin cleanup occurs through membership-removal events, with no independent sweep of shared credential rows |
| Network-user deletion                                       | All credentials, handles and account plugin metadata for that user removed                                                                      |
| Single-site user deletion                                   | That user's credentials, handles and account plugin metadata removed                                                                            |
| Deactivation                                                | Persistent data retained                                                                                                                        |
| Uninstall                                                   | All plugin-owned data removed throughout the installation/network                                                                               |

Lifecycle cleanup follows an independently authorized WordPress account/site/plugin deletion; it is not a voluntary credential-management operation and is not blocked by the usable-access rule. It provides no emergency-revocation endpoint or exemption for ordinary administrator credential removal.

## 12. Relying parties and origins

The default RP ID is the host of the configured canonical WordPress site URL. RP display name and domain are configurable. Verification uses explicit permitted origins and a valid RP relationship.

Origin handling accounts for scheme, host, IDNA, port and origin-only syntax. Arbitrary Host or forwarding headers cannot establish a trusted origin. The server relies on WordPress's configured HTTPS interpretation, without separate plugin heuristics for trusting forwarded headers. Hosting and WordPress configuration establish reverse-proxy trust and HTTPS recognition. Browser secure-context and WebAuthn availability checks determine client capability separately; they do not replace server-side RP, origin, challenge or cryptographic-proof verification. Production authentication requires HTTPS. HTTP is permitted for development only on localhost: a plain-HTTP ceremony request is accepted only when both the site URL's host and the request's host are `localhost`, and a plain-HTTP origin is accepted only for the host `localhost`. Every other host requires HTTPS and remains subject to RP and browser validation.

The Passkey domain must be `localhost` or a domain name; Settings save and RP ID canonicalization reject IP addresses, meaning any value whose last label is all digits, because browsers refuse IP addresses as RP IDs. An RP-setting change does not relabel enrolled credentials or make incompatible credentials usable. There is no additional RP-change confirmation or enrollment-invalidation notice. Parent-domain RP configuration does not implicitly authorize every subdomain origin.

Related-origin configuration is stored and published at `/.well-known/webauthn`; its settings control is hidden. The public response is JSON with an origins array and allows cross-origin reading. An empty configuration returns an empty array. Blank or invalid stored entries are omitted; published values contain the parsed scheme, host and optional port only. Publication does not enable cross-domain authentication. Omitted origins are retained on site settings saves and cleared on network settings saves. Publication does not alter verification's origin policy.

## 13. Ceremonies, verification and concurrency

Ceremony state contains its identifier, purpose, challenge and verification options. Enrollment state includes the initiating actor, login session, target account and name; test state includes the selected target. Expired state cannot complete. Enrollment completion uses the bound target account and requires the same actor and login session. Anonymous login attempts are bound to the initiating browser. Authenticated login and test attempts are bound to the initiating browser and the same WordPress session. Loss or change of the binding cookie, session or authentication context requires a fresh attempt. Tests retain their selected target and permission checks. Authenticated login completion leaves the existing session unchanged. These bindings add no setting or recent-authentication requirement.

Anonymous login-options requests are limited per client address (`REMOTE_ADDR`, after the site's own reverse-proxy configuration). Each address may start at most 30 per minute, counted in a WordPress transient keyed by an HMAC of the address. A per-address MySQL named lock covers the read and the increment, so concurrent requests cannot share one count; if the counter cannot be locked or saved, the request is treated as over the limit. Over the limit, the request returns `rate_limited` before an attempt is stored. There is no site-wide cap, because one would let a handful of addresses lock out every visitor. Each anonymous insert first deletes up to 100 expired attempts, so the table holds only unexpired ones. Setup options requested from a signed-out browser count against the same per-address limit. Signed-in requests, tests and enrollment are not limited this way. Behind a reverse proxy that does not restore the client address, every visitor shares one count. Uninstall removes stored counters.

Challenges and identifiers use cryptographically secure randomness. Management operations use WordPress nonces. Login and test attempts use the browser/session bindings described above. A nonce does not constitute reauthentication.

After basic authorization and ownership checks, at most one completion request atomically claims a registration, login or test attempt before verification. Duplicate completions and replays are rejected without credential or session side effects. A claimed attempt cannot be reused, including after verification failure or interruption; retry requires a fresh ceremony. A lost response does not establish failure: the claimed request may have completed, and feedback distinguishes an uncertain outcome from a confirmed failure. Expiry is checked during requests independently of scheduled cleanup. The browser timeout hint is 60 seconds and server lifetime is 90 seconds.

Submitted purpose must match the issued purpose. Verification checks protocol fields, challenge, origin, RP hash, credential ownership, user presence, required user verification, signature, algorithms and backup invariants. A missing UV flag fails every ceremony.

Credential identifiers are binary-safe, with full-byte equality checks and unique ownership constraints. A hash index does not replace full equality. Stored records contain explicit fields rather than serialized PHP or verifier object graphs.

Login and credential tests succeed only after any necessary credential security-state update is confirmed persisted. No login session is issued before that confirmation. A confirmed unchanged security state is acceptable; zero affected rows alone does not establish failure. Failure to persist a necessary security update fails the attempt. Failure affecting only the informational last-used timestamp does not block otherwise valid login or test success; the interface does not claim that an unsaved timestamp was stored. Successful credential deletion and final authentication acceptance have one atomic server-side ordering. If deletion completes first, authentication is rejected. If authentication is accepted first, it may finish. Deletion does not terminate established sessions or undo an already-accepted authentication. Response or cookie delivery order does not determine this ordering. The usable-access safeguard still governs whether deletion is permitted. Synced credentials and zero counters follow the explicit counter and backup-state rules in section 17.

Malformed input produces a request or verification error.

Ceremony policy timing is defined per field. A blanket restart requirement for every policy change is not part of the user flow. The completion checks below also govern the final locked acceptance check; "eligibility" does not mean reapplying every current setting to issued options.

| Policy or state | At issuance | At completion and final acceptance |
| --- | --- | --- |
| User verification | Always request required | Reject completion unless UV is verified |
| Test allow-list | Include the target account's eligible credentials under the RP and account rules | Require membership in the issued allow-list; removed credentials still fail |
| Login eligibility | Issue discoverable options without a credential allow-list | Verify ownership, RP compatibility, required UV and a matching user handle |
| Remember me | Bind the requested selection; true requires the setting enabled | If true was requested and the setting is now disabled, reject with `invalid_request`; false remains non-remembered |
| RP and permitted origins | Store the explicit RP and permitted origins | Require the issued proof and current RP/origin compatibility; a configuration change can invalidate the response |
| Actor, target, browser/session, permissions and account existence | Establish the required context | Recheck the approved binding/authorization/account rules; changed or missing required context fails |
| Credential existence, owner, key, counter and backup state | Read the credential used for verification | Confirm the verified snapshot and permitted state transition under the owner lock; revocation and security-state persistence rules remain mandatory |

Settings changes affect newly issued ceremonies immediately. Credential lists and voluntary-removal access assessments always describe current policy, independently of an outstanding ceremony's issued options.

## 15. Diagnostics, localization and accessibility

Logging is disabled by default. Enabled logs remain until manually cleared, with no automatic age-based expiry or automatic disabling. The viewer provides a count and a manual clear action, disabled when the log is empty. It refreshes every five seconds while logging is enabled; retained logs displayed with logging off do not start automatic refresh. Log read/clear requires manage_options and an administrator nonce.

Enabling logging appends initialization entries for environment versions, configuration and extension-provided information. Disabling logging retains entries. Logs redact authentication responses, tokens, sensitive headers, secrets and unnecessary identifying data. Configuration, dependency and HTTPS warnings provide actionable failure information and correlation identifiers without exposing authentication material.

English is the source language and default fallback; no separate English translation catalog is required. French is packaged for exactly two additional locales: `fr_CA` and `fr_FR`. English and both French locales cover all user-facing strings, including PHP, administration, native login, frontend JavaScript, shortcodes, Gutenberg editor controls, notices and operation/error messages. The plugin neither forces `fr_FR` globally nor adds a language-switching interface. A shared neutral French translation source may supply both separately packaged locale catalogs. Other French locales have no implicit French-catalog fallback; missing translations fall back to the English source string.

Interfaces use labeled form controls and textual progress/success/failure messages. In Passkey only mode the native login page focuses the "Sign in with a passkey" button. The own-profile after-registration marker focuses the Add passkey button.

## 17. Runtime and dependencies

The browser uses native WebAuthn, DOM and HTTP APIs. WordPress supplies account and capability services, sessions, database access, translation, scheduling and editor integration. PHP supplies secure randomness and hashing. OpenSSL is the only optional PHP extension permitted as a dependency of the plugin or its runtime libraries. Text handling, binary decoding and other operations require no additional optional PHP extensions. Mandatory facilities built into the selected PHP runtime remain available. WordPress retains its own hosting and database prerequisites. Database tables must use InnoDB, not MyISAM (see sections 20 and 21). Otherwise activation fails with "Passkey storage could not be initialized. The database tables must use the InnoDB storage engine." Activation checks every site's options table on multisite. Any other failure while creating or checking the tables shows "Passkey storage could not be initialized." Cryptographic operations use OpenSSL or established libraries; protocol and signature verification requirements remain unchanged.

The plugin uses WordPress and PHP URL utilities with explicit WebAuthn origin validation and canonicalization.

Server-side WebAuthn verification uses `lbuchs/webauthn` v2.2.0 for CBOR/COSE and authenticator-data processing, protocol checks and signature verification through OpenSSL. Registration offers ES256 and RS256 with direct attestation. The supported RS256 key representation has a modulus of exactly 256 bytes and an exponent of exactly three bytes, as required by the pinned verifier. Other RSA key representations fail registration with `authentication_failed`; no credential is stored and no alternate algorithm or library is substituted. OpenSSL provides SHA-256, P-256 and RSA support. The plugin requires WordPress 6.9 or later and PHP 8.3 or later. The library's own PHP 8.0 minimum does not lower the plugin requirement.

The plugin validates exact permitted origins and their RP relationship, credential ownership, user handles and membership in any issued credential allow-list. Issued and accepted algorithms are restricted to ES256 and RS256. Backup state cannot be set without backup eligibility, and assertion backup eligibility must match the stored credential's eligibility. Verified backup state and counters follow the security-state persistence rules in section 13. A zero counter is a valid value, distinct from missing state: two zero counters are accepted; when either stored or received counter is nonzero, the received counter must exceed the stored counter. A nullable library accessor does not erase an explicitly received zero. Session binding, single-use attempts, permissions and revocation ordering remain governed by sections 7 and 13.

Distribution includes the library's required MIT copyright and permission notices. The project is licensed under GPL-3.0-or-later. Bundled third-party components retain their own license and attribution notices.

Browser capability detection determines available passkey features and policy-permitted fallbacks.

The existing bound attempt supplies the context; this is not a second persisted attempt record. The protocol adapter's narrower `VerifiedAssertion` return is combined with this server-held context by Passkeys. Proof is scoped to the current request, never returned to JavaScript or treated as a reusable token. A diagnostic append failure does not change the operation/authentication result and does not recursively log itself. Settings owns the disabled-to-enabled initialization event and invokes `azwp_passkeys_log_initialization` outside the transaction. It captures the pre-save configuration for those entries and appends them after a confirmed successful enable save, before subsequent setting-change entries. Disabling retains logs and suppresses the subsequent change entries as specified in section 25.

Each view is a template in `views/` named after its screen: `settings-site`, `settings-network`, `profile`, `login`, `frontend-login`, `frontend-register`, `frontend-test`, `credential-list` and `diagnostics`. ### Tables and types

Tables use `$wpdb->base_prefix` plus the names below and InnoDB transactions. WordPress database APIs supply the connection and prepared queries; no PDO extension is required. A duplicate hash with unequal bytes fails safely without overwriting either credential. A duplicate exact ID is rejected regardless of owning user/site. Credential ID lengths obey WebAuthn representation limits, not an arbitrary per-user credential cap. Names have no additional product length limit beyond transport/database bounds. `sign_count` is the unsigned 32-bit protocol value held in a wider column; 0 is stored explicitly. `transports` accepts a JSON array of strings; another shape fails with `invalid_request`. The stored AAGUID is exactly the 16 binary bytes received in the authenticator data of a successfully validated registration. None attestation does not cause the plugin to replace a received nonzero AAGUID with zeros. A received all-zero value remains zero and represents unavailable or unknown authenticator identity; it does not invalidate the credential. All-zero is a present value, distinct from NULL, an empty string or a missing field. Missing or malformed attested credential AAGUID input fails registration rather than being replaced with zeros. FOR UPDATE`; concurrent first use reads and locks the identity row inserted by the concurrent request rather than overwriting its handle. A handle collision belonging to another user generates another handle and retries that insertion. Provisioning alone leaves `enrollment_initialized=0`; only authorized enrollment-options issuance sets it to 1. Registration uses the handle's exact 64 bytes as `user.id`, without text decoding or truncation. Registration and assertion verification reject stored handles of any other size. Issuing the first authorized enrollment options marks `enrollment_initialized=1`, even if the browser ceremony later fails; provisioning an identity solely for row locking or an account-policy save does not mark enrollment initialized. The flag remains set after the last credential is removed and is removed with the identity on account cleanup. The database does not contain serialized PHP/library objects, private keys or raw assertion/attestation proofs. Table creation/migration fails visibly if transactional storage cannot be established; authentication does not fall back to non-atomic writes. InnoDB is a storage requirement; the numerical database support floor remains a release selection. The WordPress minimum is 6.9.

## 21. Ceremony state and atomic operations

Purposes are `register`, `login`, `test`, `setup`, and the purpose fixes the ceremony shape: registration always requires a resident credential, login is always discoverable with no allow-list and no client-selected target, and a test always carries its selected target's allow-list, and a setup always requires a resident credential for the setup link's account. `issued` contains RP ID, permitted origins, UV requirement, allowed credential IDs for tests, target ID where resolved, registration name, and the applicable remember/redirect request fields. Binary values in JSON are unpadded base64url; internal verification uses bytes. An authenticated test keeps its actor and selected target distinct.

The state machine moves from `pending` to `claimed` to `deleted`. Stored status is only `pending` or `claimed`; deleted means the row is absent, not a third stored status. Expiry makes pending state unusable even before cleanup. Claim is a conditional database `UPDATE` matching ID, receiving site, purpose, issued target where applicable, pending status, unexpired timestamp and browser/session/actor binding. The default name is fixed in the attempt when options are issued; an endpoint cannot claim an attempt of another purpose. Exactly one affected row establishes ownership. That write commits before cryptographic work. No lock is held while the browser prompts or network clients respond. A failed, disconnected or abandoned claimed request is never reset to pending. Rows are deleted after handled completion; expired rows of either status are eligible for cleanup. Tests use the same single-use state machine as registration and login.

`azwp_passkeys_browser` is a random 32-byte base64url host-only session cookie: HttpOnly, SameSite=Lax, Path=/, Secure on WordPress-recognized HTTPS and non-Secure only for the permitted localhost development origin. An options request reuses a valid existing binding cookie; it issues a fresh value only when the cookie is absent or malformed, never on every ceremony. Concurrent initial requests that receive different new values can invalidate the losing attempt and require a fresh attempt. The cookie is not issued by cached page HTML. The server stores only a SHA-256 digest. An absent/replaced cookie cannot complete an existing attempt. Authenticated attempts also bind SHA-256 of the WordPress session token and the actor ID. Cookie refusal produces an error asking the user to start again; no IP address, user-agent fingerprint or extra authentication prompt substitutes for it. Each host creates its own binding; changes to the origin or site do not inherit an attempt. Challenge and attempt ID are independently random 32-byte values. Transport uses POST and no-store responses; proof material does not appear in query strings or logs.

All credential enrollment, rename, removal, final assertion acceptance and account-password-flag changes acquire the owner's identity row with `SELECT ... FOR UPDATE` inside a transaction. Storage provisions or reads the owner identity inside that transaction before acquiring its row lock and performing the operation, using section 20's unique-insertion rules. The order is identity row, then credential rows in ascending ID order. Single-owner operations do not acquire other owners' locks. Policy saves and final credential mutations/acceptance also acquire one installation-wide database advisory lock named `azwp-passkeys:` plus the first 32 hexadecimal characters of SHA-256 of the database name and base prefix. Acquisition waits at most 5 seconds; this is an internal contention bound, not a setting. The order is this advisory lock, identity row, then credentials. This lock keeps policy unchanged while the plugin checks the remaining sign-in and recovery methods. The advisory lock is released in `finally`; a failed acquisition is an operation failure, not permission to proceed. Policy reads in that section bypass stale option/user-meta cache values and use confirmed stored values. Settings and account-flag persistence use prepared database writes to the plugin's WordPress option and metadata keys inside the coordinated transaction, followed by WordPress cache invalidation after commit or rollback. WordPress option/meta tables participating in these transactions must also be transactional. Plugin notification hooks run after commit; no generic option-update hook is required as part of the public contract. Cache invalidation covers the affected key and the site/network option cache and user-meta cache as applicable. Cryptographic verification and account-policy callbacks run before this short database critical section. No lock is held across WordPress callbacks which may redirect/exit or issue external I/O. Policy and credential changes made through the plugin obey this coordination; direct database changes outside the plugin do not have the same ordering guarantee.

For final assertion acceptance, signature verification can occur before the owner lock. Under lock, the stored credential must still exist, retain the verified owner, RP and key, satisfy the field-specific eligibility timing in section 13, and have a counter compatible with the verified response. The request-private acceptance proof in section 19 supplies the verified snapshot and bound attempt context for these comparisons. The transaction confirms required counter/backup updates and commits acceptance. A concurrent removal taking the lock first makes this fail; acceptance first can finish issuing its session after lock release. The ordering is database acceptance, not response arrival. A concurrent assertion with a stale counter cannot overwrite a newer counter. Informational last-use saving is separate and its failure does not reverse accepted proof.

Normal owner-state mutations perform a fresh database check that the account still exists inside the owner transaction; cached user objects or an earlier database snapshot do not establish existence. This guard covers credential insertion, enrollment identity initialization, signed-in account-bound attempt creation and account-password-policy writes. Anonymous login attempts change no owner state: they are inserted without the owner lock or the installation-wide advisory lock, after a direct read confirming any resolved target account exists. Holding no shared lock keeps unauthenticated requests from delaying other operations. Account-bound attempts also require their referenced actor/target accounts still to exist. A missing required account fails the operation and rolls back any provisional identity insertion. Lifecycle cleanup may operate on an already-deleted account solely to remove its remaining state; it leaves no provisioned identity behind. Registration commits the intended complete row before success; a confirmed failed insert returns a failure, while an unknown commit outcome returns an unconfirmed result. Rename confirms stored equality; removal confirms absence only after authorization and confirmation that a usable sign-in or recovery method remains. Zero affected rows is interpreted from read-back state and the database error, not treated automatically as failure. No automatic replay occurs after an uncertain commit. Database deadlock/timeout produces a fresh-attempt or refresh outcome as appropriate; it never reuses a claimed ceremony.

To determine whether a usable sign-in or recovery method remains, the plugin checks server-observable facts: credential existence/owner, RP compatibility with the current management site's configured origins, account/site availability, and effective password/reset policy. It cannot establish whether a device or security key is lost or whether a user remembers a password; the UI does not claim those facts. A password method requires a nonempty WordPress password hash and permitted password authentication. A reset method also requires effective permission to complete reset and use the resulting password. Operator database access is not counted as user recovery. The assessment protects access on the current management site under its effective policies. All remaining credentials belonging to the target are considered, including those enrolled on other sites, but only credentials usable on this site count. Access available solely on another incompatible site is insufficient. This assessment does not require a network-wide enumeration of sites or claim to guarantee access to every network site.

`azwp_passkeys_cleanup` is scheduled once on the installation main site, with no arguments, and runs through WordPress cron hourly, removing only expired ceremony rows; request-time expiry remains authoritative. It never expires diagnostics. Network deactivation (or single-site deactivation) unschedules that main-site event and retains data. Site initialization does not schedule another cleanup event; reactivation schedules it only if absent. Lifecycle credential cleanup uses the same owner serialization but bypasses the voluntary-removal safeguard solely for the authorized lifecycle events in section 11.

Error HTTP/code mapping is: 400 `invalid_request`; 401 `authentication_failed`; 403 `forbidden` or `invalid_nonce`; 409 `attempt_unavailable`, `credential_exists`, `access_required` or `state_changed`; 429 `rate_limited`; 503 `not_configured`, `storage_failed`, `outcome_unknown`, `mail_failed`. `no_credentials` uses HTTP 409 and is allowed only for authenticated management/tests; public login failures complete as `authentication_failed`. `cancelled`, `unsupported`, `network_error` are local UI conditions, not server verification claims. Error details, SQL and cryptographic internals are not exposed. Account/authentication `WP_Error` results are mapped to the same JSON failure envelope and translated inline message, without exposing internal error detail or introducing an error-code UI setting.

Credential summaries contain `record_id`, `name`, nullable `authenticator` (the catalog model name), `synced` (the stored backed-up flag), `created_local`, nullable `last_used_local`, `available`, `unavailable_reason`, `can_rename`, `can_remove`. They never contain public keys, handles, counter details or credential proof. `available` indicates whether current policy permits this passkey; `can_remove` is an advisory snapshot and is checked atomically again on removal.

## 23. WebAuthn adapter and origin contract

The adapter uses the pinned library without modifying its source or cryptographic algorithms. Creation user fields contain the stable opaque handle as `id`, the account login as `name`, and its WordPress display name as `displayName`; the browser creation call does not include an avatar URL. Creation and assertion options explicitly pass `required` for user verification in every ceremony. Both verification methods require the UV flag. Creation always sets `residentKey` to `required`. Returned creation parameters are limited to ES256/RS256 even if the host offers EdDSA. Attestation is `direct`, and the accepted formats are `WebAuthn::ATTESTATION_FORMATS` in section 19. A received statement must verify; the result only names the authenticator model and never grants trust. Test assertion options include only the target's eligible stored credentials; login options omit `allowCredentials`. Creation options omit `authenticatorSelection.authenticatorAttachment`. All supported passkeys are permitted, subject to the required cryptography, user verification, ownership, account and RP/origin checks. Credential descriptors may carry their stored actual transport metadata; empty metadata omits the transport member. No category-derived transport override is applied. Login requests have no credential descriptors. Transport hints guide browser selection and never replace server eligibility checks.

Canonical origins contain scheme, ASCII host and optional non-default port, with no path, userinfo, query or fragment. Comparison is exact after lowercasing scheme/host and removing default ports (HTTPS 443, HTTP 80). RP IDs contain only the canonical host, never scheme/port/path. DNS suffix matching requires a dot boundary; `badexample.com` is not a subdomain of `example.com`. Parent RP configuration does not authorize arbitrary subdomains. Host/request/proxy headers, referrers, redirect destinations and the published related-origin document cannot add permitted origins. `null` origins, Android application origins and cross-origin embedded ceremonies are rejected. Browser top-level `crossOrigin` is absent or false; a true flag cannot be overridden by client extension output.

Configured URL paths are discarded when deriving their origin, while incoming clientData origin must already be origin-only. WordPress/PHP URL utilities perform structural parsing. ASCII IDNA A-labels are supported without `intl`; canonical configured A-labels are compared with the browser's A-label host. Unicode configuration uses WordPress's bundled Requests IDNA encoder where available; invalid encoding fails configuration validation. If that encoder is unavailable, non-ASCII configuration receives an RP field error; canonical ASCII A-label configuration remains usable. There is no dependency on an optional extension or silent ad-hoc conversion. Punycode conversion alone does not establish public-suffix validity. RP configuration must be the exact origin host or a registrable parent of it; the browser enforces its WebAuthn RP constraints, and server acceptance also requires exact stored origins, explicit RP selection and matching RP hash. No network metadata lookup expands RP trust. Permitted origins are the canonical origins of the receiving site's configured WordPress site URL and home URL, deduplicated and restricted to those satisfying the configured RP relationship and HTTPS/local-development rule. The values come from WordPress configuration (including its configured URL constants), not request headers or a submitted destination. The exact permitted set is stored with the attempt and checked again against current configuration at completion. An unrelated home host is excluded rather than broadening the RP. A frontend on a distinct permitted host still requires working WordPress AJAX/cookie routing; origin permission alone does not supply CORS access or cross-host session cookies.

`WebAuthn::verify_registration` validates envelope type, strict binary encodings, clientData type/challenge/origin/context, UP, required UV, RP hash, attested credential presence, nonempty credential ID and equality with rawId, offered algorithm/key type/curve, a supported attestation format whose statement verifies (none requires an empty statement) and backup invariants. Passkeys and Storage enforce duplicate ownership with the global credential constraint and confirmed insertion; the protocol adapter does not query storage. The verifier returns `{credential_id, public_key_pem, public_key_cose, credential_type, attestation_type, trust_path, aaguid, other_ui, transports, algorithm, sign_count, backup_eligible, backed_up, rp_id}` with the field semantics in section 20. The selected library supplies raw AAGUID bytes; the adapter validates their 16-byte shape and returns those bytes unchanged after successful registration verification. COSE bytes are the validated key item from authenticator data, not a re-encoded attestation object. It does not infer storage location or provider identity from transport hints, or store attestation certificates.

`WebAuthn::verify_assertion` validates the resolved stored owner, exact credential ID, any issued allow-list, and matching userHandle when supplied. Login requires a nonempty matching opaque handle; tests permit a null handle but reject a supplied mismatching/empty handle. It checks clientData, origin, RP hash, UP, required UV, ES256/RS256 signature, counter semantics and backup eligibility continuity. The signed bytes remain unchanged. It returns `{credential_id, owner_id, sign_count, backup_eligible, backed_up}`. The plugin stores explicit zero, rather than confusing a nullable library counter accessor with absence. Assertions and tests leave AAGUID, COSE key, credential/attestation types, trust path, auxiliary UI data and transports unchanged; rename changes only the display label, and deletion/lifecycle cleanup removes the whole credential record. Backup eligibility never changes for an existing credential; backed-up state can change only on verified assertions. Parser/library exceptions become application errors at this boundary, not PHP warnings in a response. Invalid/unsupported input cannot cause a fallback to password or another algorithm.

## 24. WordPress integration and lifecycle mechanics

### Login and cookie completion

Login controls attach through `login_form` and `login_enqueue_scripts` on the login form; registration, lost-password, reset-password and administrator-email-confirmation forms are not rearranged into passkey login forms. Explicit login completes through AJAX on native and frontend login pages. Browser cancellation, verification rejection and account/cookie-policy failures remain on the initiating page with restored controls. Successful login returns a server-validated destination and the browser navigates 200 milliseconds after its success message. The embedded traditional password form remains a normal WordPress login form.

Anonymous completion first claims and verifies the bound attempt and resolves its proven account. A request-private proof context records the verified ID and pending security-state update. Only that AJAX operation installs scoped `authenticate` callbacks around `wp_signon()` with the canonical account login and an empty password. The early callback at priority 19 preserves an existing `WP_Error`, supplies only the proven `WP_User`, and explicitly applies `wp_authenticate_user` with an empty password because core password callbacks otherwise short-circuit for a supplied user. No dummy password or client-supplied account is accepted as proof. Verification failure returns JSON before sign-on; no submitted password can turn a failed proof into success.

The terminal scoped `authenticate` callback at `PHP_INT_MAX` preserves errors, rejects another returned account, rechecks account eligibility and commits the atomic security-state acceptance. It never supplies a fallback user after denial. `wp_signon()` then handles cookies and the single `wp_login` event. Scoped callbacks are removed in `finally`. Explicit multisite spam/deleted/nonexistent-account checks remain effective; proof does not grant membership. The adapter does not broadly remove authentication callbacks or promise compatibility with arbitrary password-specific plugins. Account checks that return an error remain authoritative.

The adapter observes `send_auth_cookies` and the new sign-on token without overriding an unrelated false result. A request-scoped early `wp_login` handler detects suppression, destroys only that newly created token and terminates the operation with the JSON failure envelope before other success actions. Other sessions remain. After successful sign-on the adapter sets the current user for this request and returns success. If the response is lost, the browser cannot confirm the result; the server cannot prove that a browser stored its cookie. Authenticated login completion skips `wp_signon`, `wp_set_current_user` and cookie creation; tests never enter sign-on. Both retain the existing actor/session.

Destination selection uses the specified native/frontend requested values and defaults, applies WordPress's `login_redirect` filter with the authenticated account, and applies `wp_validate_redirect` with WordPress's allowed-host rules and the `wp_safe_redirect_fallback`-filtered administration URL before returning a URL. Native default destinations follow WordPress's role/capability-sensitive admin/profile/home choice; frontend defaults retain the containing page. This is AJAX authentication with WordPress account, cookie and redirect integration. It does not execute the `wp-login.php` post-login page controller and does not reproduce its interim-login document or administrator-email-confirmation interstitial. Native password login retains those core flows. The passkey UI does not claim to complete an embedded interim-login handshake; its specified success operation is navigation to the safe destination.

The Two-Factor adapter is scoped to the server-verified user and current passkey sign-on request. `two_factor_is_required_for_user` returns false for that context only and leaves other users/requests unchanged. Provider settings and persistent metadata are never changed. Without that filter the plugin does not remove generic filters to force a bypass; such versions are outside the supported integration contract. The integration requires Two-Factor 0.17.0 or later.

### Password and reset hooks

Password-login restriction applies to WordPress account-password authentication through `wp_authenticate_user` and a late `authenticate` guard for the normal password login path. Verified passkey requests are exempt from the account-password restriction only, not account status checks. `application_password_did_authenticate` marks application-password requests separately: application passwords and already-authenticated admin actions are not blocked as account-password login. Calls to `wp_check_password` in unrelated operations are not filtered. Admin profile password controls and saves remain native.

The strict session rule in section 2 uses three hooks. `attach_session_information` marks a session `passkey` or `registration` in its session data while the plugin's own sign-on creates it. `auth_cookie_valid` records the token of the cookie that identified the user in this request. `determine_current_user` at priority 30, after core cookie and Application Password resolution, checks that token when password login is disabled for the account: a session without either mark is destroyed and the filter returns false. A user resolved without a cookie, such as through an Application Password, has no recorded token and passes unchanged.

Passkey only mode adds these hooks. `login_body_class` adds `azwp-passkeys-only` so CSS hides the native fields. The reset hooks above treat the mode as "For everyone". `wp_send_new_user_notification_to_user` marks the new account so that `allow_password_reset` allows the single key request WordPress makes to build the welcome email. `wp_new_user_notification_email` then replaces the welcome email's set-password text. The setup link uses `login_form_azwp_passkeys_setup` for its page and `login_message` for "Passkey added. Sign in with it now." The readiness link uses `users_list_table_query_args` to limit the Users screen to members without a passkey when `azwp_passkeys_missing=1` is present and the viewer can `list_users`.

`allow_password_reset` implements the off/except_admin/everyone permission rule using the acting user's `edit_users`, preserving an existing denial. Native `login_form_lostpassword`, `login_form_retrievepassword`, `login_form_resetpass` and `login_form_rp` requests are returned to login when reset restriction is on, including an administrator visiting those public URLs. Lost-password links and the default-password reminder are hidden in restricted modes. These controls do not hook password storage or remove admin profile password fields.

`show_user_profile` renders self management; `edit_user_profile` renders target management only with `edit_users` and `edit_user(target)`. Own-profile and user-edit saves reach the plugin through `user_profile_update_errors`, which runs before WordPress writes the user. The plugin saves the account-password flag there only when no other field failed, with native target nonce/capability checks. Flag changes use the coordinated persistence contract in section 21, including cache invalidation after commit or rollback. Global Passkey only mode renders a disabled checked control; its forced presentation never overwrites the independently stored account flag.

WordPress owns account registration, welcome emails and registration continuation. When `after_registration` is `add_passkey` on a single-site installation, the plugin adds one `register_new_user` handler at priority `PHP_INT_MAX`, so WordPress's `wp_send_new_user_notifications` and other handlers run first. The handler receives the new user ID and acts only when `$GLOBALS['pagenow']` is `wp-login.php` with request action `register`, `is_multisite()` is false, the setting is `add_passkey`, `get_current_user_id()` is 0 and the account passes the same availability check as passkey login. It then requires the request origin check from section 4: `$_SERVER['HTTP_ORIGIN']`, or the scheme/host/port of `$_SERVER['HTTP_REFERER']` when Origin is absent, canonicalized with section 23's rules and compared exactly against the site's permitted origins. Request host or forwarding headers do not add permitted origins. It applies `wp_authenticate_user` to the new `WP_User` with an empty password, exempting only the plugin's own password-login restriction for this request; any `WP_Error` result ends the handler without a session. The remaining steps run in this order:

1. Observe `send_auth_cookies` as in the login adapter above, then call `wp_set_auth_cookie($user_id, false)`.
2. If cookies were suppressed, destroy only the newly created session token and return. Do not set the current user or fire `wp_login`.
3. Call `wp_set_current_user($user_id)`.
4. Fire `wp_login` once with the account login and `WP_User`. A Two-Factor handler that takes over the request here keeps control, and step 5 does not run.
5. Call `wp_safe_redirect(add_query_arg('azwp_passkeys_registered', '1', admin_url('profile.php')) . '#azwp-passkeys')` and exit.

`registration_redirect` and the register form's `redirect_to` are not applied. Every failure path returns without output, so WordPress continues to `wp-login.php?checkemail=registered`. The outcome is logged as `registration_sign_in` with `result` `ok`, `cross_origin`, `denied` or `cookies_suppressed`.

### Lifecycle

Activation registers schema with `dbDelta`, verifies transactional engine/required indexes, initializes defaults without overwriting existing values, and schedules cleanup. Multisite activation requires network activation and initializes the shared tables plus site options; `wp_initialize_site` applies defaults to new sites. An incomplete schema makes operations unavailable with an administrator diagnostic rather than partially writing credentials.

`remove_user_from_blog` deletes only the removed membership's enrollment-site rows. Final `deleted_user` handling runs on both single-site and multisite. Under owner serialization, a fresh database read must confirm that the WordPress user row no longer exists before full cleanup removes that owner's credentials, attempts, handle and plugin user metadata. If the user still exists, this event performs no account-wide cleanup: site membership cleanup remains solely the site-scoped `remove_user_from_blog` operation, and other-site credentials, the handle and global account flag remain intact. Multisite `wpmu_delete_user` may perform the same idempotent early cleanup but does not replace final cleanup after WordPress removes the account. If an enrollment commits between early cleanup and account deletion, final cleanup removes it; if final cleanup completes first, the owner-state transaction's fresh account-existence check rejects recreation of credentials, handles, bound attempts or account metadata. Cleanup does not recreate enrollment state or preserve credentials for a deleted account. There is no separate `wp_delete_site` sweep of shared credential rows. Deactivation unschedules cleanup and retains data. Uninstall removes the four shared tables, plugin site/network options across the installation, plugin user metadata, scheduled cleanup and related-origin routing state. Only plugin-owned data is removed. Browser cookies cannot be removed from every device by uninstall; they contain no credential authority without server state.

The public `/.well-known/webauthn` response uses a WordPress rewrite/query handler (`azwp_passkeys_related_origins=1`), JSON `{origins:[...]}`, `Content-Type: application/json` and `Access-Control-Allow-Origin: *`. It accepts GET without credentials. Invalid entries are omitted, paths are stripped from stored URL entries for publication, and an empty array remains valid. Activation and deactivation flush rewrite rules. Site initialization and uninstall delete the stored rules so WordPress regenerates them on the next request. Ordinary requests never flush them. This publication does not supply the authentication origin allow-list.

Enrollment, sign-in and test help states: "Confirm with your fingerprint, face, or device PIN. This is required to continue." Devices without this capability receive an operation error and cannot complete the action. Credential-name help explains that the label does not affect authentication, and enrollment help identifies the target account and permits multiple credentials.

When the configured environment lacks required OpenSSL capabilities or a permitted secure context, the UI explains the problem and disables the Enable choice of Passkey only mode while it is off. The profile's Add passkey button is disabled; Test passkey stays enabled so clicking it can display capability feedback. The account's Passkey only mode checkbox is disabled for editing in that state. Existing effective password restrictions remain visibly identified and stored; a disabled or omitted control does not clear them on an unrelated save. Disabled settings controls carry their persisted value in a hidden field so the required save schema still applies; the account flag retains its stored value server-side when its editing control is disabled, independently of global policy presentation. Policy enforcement remains independent of secure-context detection.

The button is "Save changes". A successful save shows "Settings saved". A failed save shows "Settings could not be saved." The form retains persisted values and identifies invalid fields without exposing internals. Empty-field warnings appear beside Website name and Passkey domain. Passkey only mode notices explain that a usable passkey is needed; they do not add a confirmation gate or prevent the specified save. No logs are automatically cleared by a settings save.

The dedicated diagnostics page has the "Logging" Enable/Disable radio group and its own "Save changes" button, an entry count, a chronological text viewer and "Clear logs"; clear is disabled when empty. Enabled logging refreshes every five seconds; disabled logging displays retained entries without polling. A failed refresh replaces viewer text with a loading-failure message; stored entries are unchanged and a later successful refresh restores them. The viewer scrolls to its end after initial load or changed fetched text; unchanged polling preserves its scroll position. Clear success resets count/view after confirmed deletion. Initial events include plugin/PHP/WordPress/library versions and non-secret effective configuration. Event keys are `log_initialized`, `settings_saved`, `registration`, `authentication`, `credential_test`, `credential_renamed`, `credential_removed`, `registration_sign_in`, `storage_error`, `configuration_error`, `account_cleanup`, `membership_cleanup`; each records result and correlation, not proof payloads, passwords, cookies, tokens, challenge values, public-key material, request headers or raw SQL. Log detail uses a fixed allow-list of fields, not wholesale request serialization. Settings-change entries identify each changed nonsecret setting and its previous/new values. Initialization entries occur only on a disabled-to-enabled logging transition and describe the pre-save configuration. Logging is enabled before recording subsequent setting changes and disabled before processing subsequent changes when turned off. Network setting changes log in the current site's diagnostic scope. Account and membership cleanup record their lifecycle outcome without raw usernames or credential proofs.

### Profile and list controls

The checkbox label is "Passkey only mode", with help "Turn off password sign-in for this account." Global Passkey only mode adds a network/site-policy explanation. This checkbox belongs to native profile save. Credential controls do not submit that profile form. Never-used time is "—". Empty text is "No passkeys added." A credential unusable under the current site settings shows text explaining the reason.

Columns are Name, Authenticator, Added, Last used and Actions. The Name cell holds the label and a "Rename" text link; the Actions cell holds the "Remove" button. Rename uses the current label as the initial prompt; cancellation/unchanged input has no request. Remove confirmation identifies the credential label and explains server removal does not erase the device credential. A blocked last-method removal says "Add another usable passkey or restore another sign-in method before removing this passkey." An already-absent result refreshes the list and does not claim a new deletion.

On the own-profile page, the `azwp_passkeys_registered=1` query marker focuses the Add passkey button on load and shows the after-registration message from section 4 in its status region. The marker is ignored on other users' edit pages and is not carried into management requests.

"Add passkey" and "Test passkey" sit side by side below the list and start their browser ceremonies immediately. On another user's edit page a third button, "Send passkey setup link", emails that account a setup link and reports "Setup link sent to the account email address. It expires in one hour."; there are no panels and no name field. Both report progress and results in one shared status region. On another user's edit page the selected target is identified. Handled enrollment/management success or failure refreshes the list; tests refresh it after success. A successful test displays `Passkey test passed for “%s”.`, where `%s` is the label of the credential that answered, and updates the displayed last-use time only if it was stored. Login displays "Passkey verified."

### Login and shared component states

With Passkey only mode off, the native login form keeps WordPress's fields and appends "or" and "Sign in with a passkey" after Log In. With it on, the passkey form shows the device-verification help, conditional "Remember me" and "Sign in with a passkey", receives focus, and the page body carries the `azwp-passkeys-only` class that hides the native fields. It has no identification field. Its traditional form is produced by `wp_login_form` with return rather than direct echo, the required default username, and the containing-page/requested redirect; it uses normal WordPress form submission.

Pressing Enter in the native login form submits the password form when Passkey only mode is off and starts the passkey action when it is on. When the browser prompt is cancelled or no passkey is chosen, login shows "Passkey prompt cancelled. Try again or use a password." when Passkey only mode is off, and "Passkey prompt cancelled. Try again." otherwise. Account resolution failures remain generic.

Every rendered component has a unique DOM ID and `data-azwp-passkeys` role. Delegated listeners are installed once. Action disabling applies to all page passkey action buttons, and requested return destination uses the first matching destination field, as specified. Multiple instances do not duplicate event handlers or create parallel requests from a single click. Page pending state ends after handled success/failure/cancel; completed claimed attempts are not resubmitted.

### Blocks and shortcode serialization

Block names are `azwp-passkeys/login`, `azwp-passkeys/register`, `azwp-passkeys/test`, `azwp-passkeys/list`. Titles are "Passkey sign-in", "Add passkey", "Test passkey", "Passkey list". Their WordPress editor icons are respectively `admin-network`, `plus-alt`, `sos`, `menu`, with translated passkey search keywords. Login attribute schema is `{traditional:boolean=true, username:string='', auto_hide:boolean=true, to:string=''}`; others use `{display:boolean=true}`. Saved output is exactly the corresponding shortcode text with explicit serialized values, not credential HTML. Boolean values serialize to lowercase `true`/`false`; string attributes use double-quoted values with literal ampersands, double quotes and square brackets encoded as HTML entities. Rendering decodes these entities exactly once before field sanitization, so values cannot close an attribute or inject another shortcode. Editor parsing round-trips quotes, ampersands and URL query parameters. The editor uses checkbox/text controls with the same meanings as section 10. Shortcode rendering remains the single runtime source for both blocks and direct shortcode insertion.

## 26. Distribution and compatibility contracts

The plugin is not distributed through WordPress.org. Releases are GitHub releases built by `.github/workflows/release.yml` when an annotated `vX.Y.Z` tag is pushed. The workflow fails unless the tag, the header `Version` and `AZWP_PASSKEYS_VERSION` match. It builds the zip with `bin/dist.sh` and update metadata from `.github/templates/azwp-passkeys.json.tpl`, using the tag message as the changelog. It attaches both to the version release and to a release tagged `latest`, which it moves to the tagged commit. The plugin entry loads the bundled `yahnis-elsts/plugin-update-checker` v5.5, source revision `845d65da93bcff31649ede00d9d73b1beadbb7f0`, unmodified and MIT-licensed. It reads `https://github.com/arisdla/azwp-passkeys/releases/download/latest/azwp-passkeys.json`, so WordPress offers each new release as a normal plugin update.

The WebAuthn dependency is pinned to `lbuchs/webauthn` v2.2.0, source revision `20adb4a240c3997bd8cac7dc4dde38ab0bea0ed1`. Distribution records that version/revision and includes its MIT license/copyright notices alongside the unmodified library source. A dependency manifest identifies source, version and revision; no floating branch or unrecorded bundled modification is part of the distribution. The project license is GPL-3.0-or-later; the dependency retains its separate MIT license and required notices. Production artifacts include entry/autoload/uninstall files, PHP modules, required browser assets, `fr_CA` and `fr_FR` PHP and JavaScript translation catalogs and dependency runtime/license files; development tests, temporary evidence, VCS metadata and environment configuration are excluded. The README opens with a project-description paragraph and a screenshot of the profile passkey section, followed by requirements, usage and development instructions. The screenshot lives in `docs/`, so it is not distributed. Development-only files are listed in `.distignore`; `pnpm dist` builds `dist/azwp-passkeys.zip` without them. The bundled `data/authenticator-metadata-catalog.json` ships with the plugin; `docs/authenticator-metadata.md` records its origin and update rules.

The plugin requires OpenSSL. It requires no other optional PHP extension. No runtime Composer installation, Node process, remote crypto service or additional PHP extension is required on the WordPress host. WordPress's bundled compatibility and editor facilities are used from WordPress rather than copied into the plugin. The plugin declares `Requires at least: 6.9` and `Requires PHP: 8.3`. PHP 8.3, 8.4 and 8.5 are compatibility verification targets; a target is not a claim of completed testing. Compatibility with WordPress releases newer than 6.9 is a verification target, not a completed-testing claim. Database, browser and Two-Factor release ranges remain selections in section 28. Runtime diagnostics distinguish missing OpenSSL/P-256/SHA-256, unavailable schema, invalid RP and browser capability failures. Unsupported environments do not silently relax verification or password restrictions.
